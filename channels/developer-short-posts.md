# 开发者平台短帖

更新时间：2026-05-21 21:21 CST

用途：给 X、LinkedIn、即刻、GitHub Discussion、Indie Hackers、Reddit 等平台准备短帖。只手动发布，不群发，不在禁止自推广的地方贴链接。

## 版本 1：PR 描述

```text
PR 描述可以短一点，但要把 4 件事写清楚：

1. 问题在哪个文件或路径。
2. 这次改了什么行为。
3. 跑了什么验证。
4. 还有什么没覆盖。

我现在给自己的 PR 都按这个结构写，维护者不用从形容词里猜风险。

本地小工具：offer-kit/tools/pr-note-builder/
边界：工具只整理表达，不替你编验证。
```

## 版本 2：README 首屏

```text
很多 README 的第一屏不是写太少，而是没有回答第一眼的问题：

- 这东西适合谁？
- 最短怎么跑起来？
- 输入输出长什么样？
- 项目现在稳定到什么程度？

如果这些不清楚，功能列表写得再长也难判断要不要继续看。

我做了个 README 诊断小工具：offer-kit/tools/readme-audit-builder/
```

## 版本 3：漏洞报告

```text
漏洞报告里，“影响”不要写成吓人的结论。

先把条件写清楚：

- Scope 是什么。
- 复现需要什么权限。
- 证据来自哪里。
- 哪些系统没有测试。
- 修复建议是什么。

审核人能复查，报告才有机会往下走。

草稿工具：offer-kit/tools/vuln-report-builder/
边界：不做未授权测试，不处理真实 secret。
```

```text
300 元 / 50 美金的小单不要卖得太大。

我会把范围压成一个结果：

- 改 3 段 PR / issue / 商品页文案。
- 整理 1 份漏洞报告草稿。
- 改 1 个 README 首屏。
- 写 1 段付款前范围确认。

范围小，交付和边界才容易说清楚。

菜单：offer-kit/services/menu.html
```

## 不发的版本

- 不写“全自动赚钱”“稳定变现”“闭环增长”。
- 不写客户、收入、合并、payout，除非已经真实发生。
- 不在无关问题下贴链接。
- 不把同一条连续刷到多个评论区。
